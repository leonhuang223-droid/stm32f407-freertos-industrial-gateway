# 嵌入式 C 检查与调整记录（2026-10-08）

整理：兆鸣嵌入式

本次依据 `embedded-c-coding` 检查项目自有固件，范围覆盖 App、设备接口、
协议、RTOS 服务与任务、Bootloader、公共镜像格式和 STM32F407 平台端口。
178 个自有 C/H 文件纳入编码检查；CubeMX、HAL、FreeRTOS、LVGL 保留上游
实现和格式，核查其集成、实际调用路径与编译结果。

项目采用抢占式 FreeRTOS、静态对象和外设所有者任务。硬件等待留在相应
所有者任务中，跨任务访问通过队列、通知或受保护的快照完成。

## 已处理的问题

| 问题 | 调整后的行为 |
|---|---|
| Relay 恢复写入失败仍更新状态、允许后续控制 | 成功写入安全态后才更新状态；失败保持挂起并允许重试；重新初始化同步安全态 |
| Storage 几何参数或回调缺失 | 构造和操作检查完整回调、容量、页/扇区及整除关系，防止零除和越界 |
| DMA RX 对无效缓冲区、位置或空指针缺少保护 | 无效发布不写内存，无效读取返回零；保留单 ISR 生产者、任务消费者契约 |
| MQTT PUBLISH 大长度加法可能溢出 | 使用减法检查 Remaining Length；密码要求用户名存在 |
| 网络关闭失败后仍释放连接状态或 OTA 租约 | 保留连接所有权并重试；关闭成功后才允许重新初始化、连接或释放租约 |
| HTTP/OTA 清理失败丢失连接状态 | 保留状态；新请求先处理旧连接；非法 OTA 状态检查不会关闭正在使用的连接 |
| CLI 超长命令被截断后尾部可能作为命令执行 | 超长行整行丢弃到换行；随后正常命令继续执行；回调输出强制 NUL 终止 |
| 深度休眠屏障可能一直等待 ACK | 增加 5 s 静默期限，超时撤销请求并恢复参与任务；检查参与者掩码和看门狗加法溢出 |
| 外设恢复失败后清除任务挂起标志 | 保留恢复标志并重试；CAN 监控锁获取失败不进入业务处理；UI 支持部分挂起回滚 |
| 诊断结构、健康和功耗统计跨任务读取 | 在短临界区复制快照，格式化输出移到临界区外；CPU 统计采用 64 位中间运算 |
| OTA 请求开始与超时取消存在状态竞争 | 请求开始与完成/取消使用相同的临界区保护，静态邮箱在迟到完成前不被复用 |
| DataHub 等待配置锁影响任务响应 | 等待上限 100 ms；失败保留已有告警信息并设置故障标志；序列号在快照锁内读取 |
| 显示尺寸、像素数量和负枚举未充分验证 | 限制有符号坐标范围；像素数匹配区域；输入、CAN、Relay 等拒绝非法枚举 |
| 定时配置超出有符号截止时间比较范围 | 采样周期、网络超时/重连间隔及 CAN 恢复间隔限制在 `INT32_MAX` 内 |
| Manifest 缺少结束括号仍可能被接受 | 明确要求对象闭合，拒绝完整字段后仅以逗号结束的文档 |
| 长函数、参数过多与接口文档不一致 | 按职责拆分任务/解析/安装流程，采用请求结构体，更新调用者和相关说明 |

CLI 分发采用只读处理表；采集、网络连接、Storage、UI、Supervisor、
DataHub 及镜像验证/安装拆为职责清楚的内部函数。新增 `.clang-format`，
统一自有源码的 80 列格式。

## 接口和生命周期约定

I2C、RS485、LCD、MQTT PUBLISH、HTTP URL 输出、CAN 处理、镜像安装/验证、
Boot Metadata 提交等原有长参数列表改为具名请求结构体。相关端口、实现、
任务和 Host Mock 已同步迁移。外部调用这些 C API 的代码需要同步适配。
镜像头、Manifest、Flash 分区和持久化记录的线格式保持原协议。

请求结构体及其指针默认只在同步调用期间借用，不能在回调返回后保留。
跨任务 OTA 请求使用 RTOS 服务持有的静态邮箱与缓冲区，其生命周期独立
于请求任务的栈；generation、期限和完成状态控制复用。

设备操作不提供通用多线程可重入保证：Network/HTTP 由 Network Task
串行执行，Flash/Staging 由 Storage Task 串行执行，显示/触摸由 UI Task
执行，传感器由 Acquisition Task 执行，现场总线由各自任务执行。
Relay/Alarm/Config 共享操作经过配置互斥锁。getter 复制状态；跨任务
调用者须采用相应锁或短临界区。启动绑定只在调度器启动前执行。

初始化依次构造总线、设备、子系统、服务、通道及任务；网络步骤接口在
初始化前配置。挂起只在所有者任务完成操作后 ACK，恢复失败保留重试状态。
网络关闭失败保留资源；持久化事务保持完成或拒绝的闭环。

## 验证结果

- CTest：16/16 通过，包括 Python 工具、编码门禁、原有业务测试，以及
  新增 `device_contracts.host` 和 `image_install.host`。
- 镜像安装测试确认损坏包不会擦写，运行槽受保护，写体失败不提交描述符，
  正确镜像先写体并验证，再提交描述符。
- RTOS 故障测试继续覆盖队列集成员消费、配置发布失败回滚、请求超时与
  迟到完成、离线网络保持心跳及真正任务停滞检测。
- GCC analyzer：202 编译单元，覆盖 94 个不同自有 C 源文件；84 个自有
  头文件独立编译；零诊断，收集到的栈帧均为 static。
- 自有 C 源码直接调用图扫描覆盖 1062 个函数，未发现递归环；此项不解析
  函数指针和厂商库回调，相关路径另按所有者和回调契约复核。
- Cppcheck：warning/performance/portability，C99、inconclusive、force；
  自有固件零诊断。厂商库未纳入此诊断范围。
- Debug/Release：Bootloader、App A、App B 编译和固件产物门禁全部通过。
- `git diff --check` 通过。

## 保留的架构约束和板级待验证项

本次完成安全缺陷修复、任务职责整理与编码门禁，并不代表完全满足 Skill
全部架构模板或完成安全认证。以下偏差和验证边界明确保留：

1. 设备/子系统对象仍公开静态布局，部分组合与任务适配代码仍读取状态。
   Skill 要求“不透明指针模式”和“禁止从模块外部直接访问结构体成员”。
   当前增加了状态查询和配置 API，但尚未把全项目迁移为完全不透明对象。
   进一步迁移需要设计静态实例存储接口并适配组合根和全部端口，不能把
   目前的公开布局当作已经实现了编译期访问控制。
2. 采用已有 FreeRTOS 所有者任务，不为每个设备另建线程和队列；同步
   底层等待有期限。字段总线的启动事件等待和配置持久化事务互斥锁仍使用
   `portMAX_DELAY`：前者是服务启动门控，后者保证已出队事务最终结算。
   锁顺序及持有者的有限硬件操作已复核，异常停滞交由 Supervisor/IWDG
   检测；这些路径不适用于要求全调用链非阻塞的 RTC 执行模型。
3. HAL/FreeRTOS 回调保留原 ABI 类型；线格式、掩码及已有配置标志保持
   兼容，未把每个整数标志改为新的枚举或设备注册框架。
4. 健康判断仍以关键任务心跳为主，服务构造位不等于业务数据新鲜度。
   业务健康、启动就绪和降级策略需按产品要求单独定义。
5. 实机验收仍需测量最深路径栈高水位、IRQ/临界区延迟、DMA 错误恢复、
   继电器安全电平、掉电中断安装、看门狗/trial 回滚及实际功耗。
   STOP/Standby capability 保持关闭，待 RTC/EXTI 唤醒及完整时钟恢复
   验证后再启用。相关步骤见
   [板级可靠性验收](reliability_power_board_validation.md)。
